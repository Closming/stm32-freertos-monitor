# STM32 + FreeRTOS 多任务环境监测终端

基于 STM32F103C8T6 的环境监测终端。下位机运行 FreeRTOS，六个任务分别负责数据采集、
传感器读取、数据处理、显示、上报和系统监控，通过自定义串口协议把数据发给 PC；
上位机用 Python 实现，负责帧解析、实时绘图和链路质量统计。

项目的重点在任务划分与共享资源管理，具体是三个问题：一条 I²C 总线上挂着两个器件、
由两个任务分别驱动，如何避免互相干扰；六个任务周期相差 20 倍（50 ms 到 1000 ms），
优先级和栈如何分配；刷屏和读传感器这类慢操作占用总线时间较长，如何限制它对快周期任务的影响。

---

## 功能特性

**下位机**

- 六任务 FreeRTOS 架构（CMSIS-RTOS v2 接口），采集、传感器、处理、显示、上报、监控相互独立
- ADC1 双通道扫描 + DMA 循环搬运，8 点滑动平均滤波
- GPIO 软件模拟 I²C，一条总线上挂 SHT30（`0x44`）与 SSD1306（`0x3C`），
  由互斥锁加优先级继承和递归锁保护
- SSD1306 驱动（自写最小实现）与 5×7 ASCII 字库
- 自定义串口协议：双帧头 + 长度 + 序号 + CRC16-Modbus，USART1 + DMA 发送
- 温度、湿度、光照三路越限判定，OLED 显示与蜂鸣器输出，按键消音
- IWDG 独立看门狗与任务心跳巡检，任一任务失去进展时给出告警
- printf 重定向，日志与协议帧共用串口并由同一把锁串行化

**上位机**

- 流式帧同步状态机加 CRC 校验，能处理错帧、丢帧、半帧和垃圾字节
- matplotlib 实时曲线、丢包率与 CRC 错误统计、CSV 数据落盘
- 离线自测模式，不接硬件即可验证整条解析链路

## 任务划分

| 任务 | CMSIS-RTOS2 优先级 | 栈 | 周期 | 职责 |
|---|---|---|---|---|
| `TaskAcquire` | `osPriorityRealtime` | 128 字 | 50 ms | 读 DMA 缓冲、8 点滑动平均、发队列 |
| `TaskSensor` | `osPriorityHigh` | 256 字 | 1000 ms | 读 SHT30（两次 I²C 事务 + 20 ms 等待） |
| `TaskProcess` | `osPriorityAboveNormal` | 192 字 | 事件驱动 | 等两路数据就绪，越限判定，分发 |
| `TaskMonitor` | `osPriorityAboveNormal` | 128 字 | 500 ms | 喂 IWDG、查心跳、驱动蜂鸣器、响应按键 |
| `TaskComm` | `osPriorityNormal` | 256 字 | 事件驱动 | 打包 + CRC16 + UART DMA 发送 |
| `TaskDisplay` | `osPriorityBelowNormal` | 256 字 | 500 ms | 刷 OLED（持总线锁最久，优先级最低） |

排序依据是实时性要求和持锁时长。采集任务优先级最高，因为 50 ms 是硬周期，它被打断太久
会让滑动平均窗口的采样间隔不均匀，滤波结果失真，整条链路都以它为节拍。显示任务优先级最低，
因为它持 I²C 总线锁的时间最长（刷一屏约 150 ms，拆成 4 段），优先级给高了会把传感器读数堵在后面。

### 任务间通信

| 机制 | 用在哪 | 为什么 |
|---|---|---|
| 队列 | 采集 → 处理 → 显示 / 上报 | 传数据，有缓冲，生产者不会阻塞 |
| 事件组 | 处理任务等两路数据到齐 | 多源同步，`osFlagsWaitAll` 等两位同时置位 |
| 任务通知 | EXTI 中断 → 监控任务 | 中断里开销最小，不需要预先创建对象 |

显示和上报用两条队列，因为队列是点对点的：同一条队列里的每条消息只会被一个消费者取走，
两个消费者共用一个队列会各拿到一半。

ADC 队列在消费端会把积压的数据全部倒掉，只保留最新一份。采集是 50 ms 一次而处理约 1 s 一次，
积压的数据只会让界面显示「过去的平均值」而不是「现在是多少」，队列在这里的作用是解耦节奏，不是缓存。

## 串口协议

```
偏移  字段     长度  说明
 0    0xAA     1     帧头 1
 1    0x55     1     帧头 2
 2    LEN      1     数据区长度（当前 = 8）
 3    SEQ      1     帧序号 0~255 循环
 4-5  温度     2     int16 大端，×100（-4000 = -40.00℃）
 6-7  湿度     2     int16 大端，×100
 8-9  光照     2     uint16 大端，ADC 原始值
10-11 电位器   2     uint16 大端，ADC 原始值
12-13 CRC16    2     Modbus CRC16，低字节在前，覆盖 LEN+SEQ+DATA
```

单帧定长 14 字节。三个取舍：

- 双帧头 `0xAA 0x55`：降低误同步概率，单字节帧头在噪声里被误认的概率太高。
- 数据区大端、CRC 低字节在前：Modbus-RTU 的惯例，串行链路上 CRC 就是低字节先发。
- LEN 独立成字段：日后加通道只需扩 LEN，上位机按 LEN 跳过未知尾部即可，老解析器不会崩。

### 帧同步

上位机用显式状态机解析，而不是 `buf.find(b'\xAA\x55')` 这种一次性切片。
真实串口是流式的，一次 `read()` 可能拿到半帧，也可能一次拿到三帧半，纯靠切片会写出一堆边界条件。

关键设计是校验失败时只后退一个字节重新找帧头，不整段丢弃。最初的实现在 CRC 校验失败时
整段重置，在「垃圾字节里恰好出现 `AA 55`」的场景下会丢掉真帧：

```
垃圾: ... AA 55 56 ...          假帧头
真帧: AA 55 08 ...              真帧头

假帧头被当成帧头 → 真帧的头两字节被当成 LEN 字段吃掉 → 整帧报废
```

后退一字节重扫之后，落在误判区间里的真帧头还有被重新发现的机会。
`Host/test_codec.py` 里有一条测试专门覆盖这个场景。

### 引脚分配

| 用途 | 引脚 | 说明 |
|---|---|---|
| 软件 I²C SCL | PB6 | 开漏输出，外接 10 kΩ 上拉到 3.3 V |
| 软件 I²C SDA | PB7 | 开漏输出，外接 10 kΩ 上拉到 3.3 V |
| USART1 TX / RX | PA9 / PA10 | 接 CH340：模块 TX→PA10，模块 RX→PA9，GND 必须共地 |
| ADC 光敏 | PA1 | ADC_IN1 |
| ADC 电位器 | PA2 | ADC_IN2 |
| 按键 EXTI | PA3 | 下降沿触发 |
| 蜂鸣器 | PB0 | 推挽输出 |
| 板载 LED | PC13 | 低电平点亮 |
| SWD | PA13 / PA14 | |

光敏不接 PA0，因为蓝 pill 的板载按键物理接在 PA0。把 PA0 当 ADC 输入时，
误按板载按键会灌入 3.3 V，读数直接饱和到 4095。所以两路 ADC 全部挪开，PA0 空置。

分压只能接 3.3 V，不能接 5 V，ADC 输入不得超过 VDDA，接 5 V 会打坏引脚。
光敏模块的供电也一样，且只用 AO 输出，DO 悬空。

I²C 需要上拉电阻。本工程只靠 GPIO 内部上拉（约 40 kΩ），只挂 OLED 一个器件时够用；
2026-09-26 挂上第二个器件（SHT30）之后信号质量不够，表现为 `scl_release_and_wait()`
拉不高（计入 `i2c_get_nack_count()`），在 SDA / SCL 上各外接一个 **10 kΩ** 上拉到 3.3 V 后消失。

⚠️ 别用 1 kΩ：开漏拉低时会有 3.3 mA 灌进引脚，两条线就是 6.6 mA，对 GPIO 过重。
⚠️ SDA 与 SCL 是两条**独立**的线，各自的电阻**不互相并联**；单条线的等效上拉是
  10 kΩ ∥ 40 kΩ ≈ **8 kΩ**。

## 技术难点记录

### 1. OLED 雪花屏：命令能通，数据写不进去

现象是屏幕亮着但显示雪花，发 `0xAE`/`0xAF` 能让屏在雪花和全黑之间交替，而刷显存无论
128 字节、256 字节、水平寻址还是页寻址都纹丝不动，把整屏写 `0xFF` 也一样。

`0xAE`/`0xAF` 有反应这一点很关键：它证明器件地址、ACK、时序和命令执行都是好的，
问题只可能在数据通道。按这个方向排查，先后在真机上否定了总线速率、上拉电阻、
芯片型号（怀疑是 SH1106）、事务长度、NAK 判定五个假设，最后定位到 SSD1306 的
I²C 控制字节语义。

> 注意这里的"上拉电阻"是针对**雪花这个问题**被否定的（当时外接 1 kΩ 无效）。
> 上拉在**另一个**问题上确实是必需的 —— 2026-09-26 挂上第二个器件后信号质量不足，
> 加 10 kΩ 上拉才解决，见「硬件与接线」一节。两件事别混起来。

SSD1306 每次事务的第一个字节是控制字节，`bit7 = Co`（Continuation），`bit6 = D/C#`
（0 = 命令，1 = 数据）。**Co = 0 表示「从这一字节起到 STOP 为止，后面所有字节都是同一种类型」**。
原代码把定位命令和显存数据放进了一个事务：

```
START | 0x78 | 0x00 | 0x21 0x00 0x7F | 0x22 p0 p1 | 0x40 | <128 字节显存> | STOP
               └────── Co=0：声明「直到 STOP 全是命令」──────┘
                                                      ↑ 这一串也全被当成命令吃掉了
```

`0x00` 已经声明后面全是命令，屏就把 `0x40` 当成 Set Display Start Line 命令执行了，
紧跟其后的 128 字节显存同样被当成命令，GDDRAM 一个字节都没写进去。

改法是把刷显存拆成两个事务，靠中间的 `i2c_bus_stop()` 切断控制字节的作用范围：
第一个事务只发定位命令，第二个事务只发显存数据。两个事务仍在同一个 `i2c_transaction()`
临界区内，总线锁全程握着，中间不会有别的任务插进来改掉定位。

### 2. 串口只发出第一帧：DMA 搬完了，但没人收尾

上电后第一帧正常，之后连轮询方式发的日志都收不到，而 LED 心跳、看门狗、OLED 都正常。
第一帧能通已经排除了波特率和接线问题，剩下只可能是发送状态没有被复位。

STM32F1 的 HAL 把「用 DMA 发 UART」拆成了两步：DMA 搬完最后一个字节后，
`UART_DMATransmitCplt()` 只是打开 USART 的发送完成（TC）中断，等最后一个字节真正移出移位寄存器；
真正把 `huart->gState` 恢复成 `HAL_UART_STATE_READY` 并调用 `HAL_UART_TxCpltCallback()`
的是 `UART_EndTransmit_IT()`，它在 USART 的 TC 中断里执行。

原工程只有 `DMA1_Channel4_IRQHandler`，没有 `USART1_IRQHandler`，NVIC 里也没使能 `USART1_IRQn`，
于是第二步整个缺失：第一帧确实发出去了，但 `gState` 永远停在 `HAL_UART_STATE_BUSY_TX`，
此后所有发送都在函数入口直接返回 `HAL_BUSY`。

补上中断处理函数并在 MspInit 里使能 NVIC 即可，两处必须同时存在：

```c
HAL_NVIC_SetPriority(USART1_IRQn, 5, 0);
HAL_NVIC_EnableIRQ(USART1_IRQn);
```

优先级必须填 5，不能更小：回调里要调 `osSemaphoreRelease()`，那是 FreeRTOS 的 ISR 版 API，
要求中断优先级数值不小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`(5)。

### 3. 报警一出现，上报和显示就永久停摆（FreeRTOS V10.0.1 时期）

第一帧上报正常，随后串口静默、屏幕冻住，而喂狗和 LED 都照常，监控任务判定数据处理任务失联。

原因在事件组。当时事件组里有三个位：两个数据就绪位和一个报警状态位。当时工程用的
FreeRTOS V10.0.1，它的 CMSIS-RTOS2 兼容层在 `osEventFlagsWait()` 里用的是严格相等判断：

```c
rflags = xEventGroupWaitBits(...);                 /* 返回的是整个事件组的值 */
if (flags != rflags) { return osErrorTimeout; }    /* 不是按位判断 */
```

而 `xEventGroupWaitBits` 返回的是整个事件组的值，不是请求的那几位。处理任务等的是 `0x03`，
只要报警位 `0x04` 也被置上，事件组的值就成了 `0x07`，`0x03 != 0x07`，兼容层直接返回超时错误。
更麻烦的是 `continue` 跳过的那一段里正好包含清除报警位，于是那个位永远清不掉，
从第二圈起每圈必挂，表现为「跑了一下就死」。

改法是把报警状态从事件组里拿出来，用一个字节变量广播即可，它本来就只是给监控任务读的状态，
单字节写在 Cortex-M3 上是原子的。同时把结论写在 `app_config.h` 和 `app_tasks.c` 里：
这个事件组里只能有那两个数据就绪位。

这个问题只存在于当时的 FreeRTOS V10.0.1。V10.3.1 的同一函数已经改成按位判断
`if ((flags & rflags) != flags)`，工程后来也升级到了 V10.3.1，所以现在的代码不会再触发它。
不过报警状态本来就不该和数据就绪位放在同一个事件组里，`app_config.h` 里保留的那条警告注释仍然有效。

---

### 4. 温湿度读不出来：数据是对的，被校验代码判成了错的

接上 SHT30 之后，OLED 上温湿度恒为 `--.--`，报警位常亮 `ALARM_SENSOR_ERR`。但**读到的数据其实一直是对的**
—— 把原始 6 个字节打出来手算核对，温度段和湿度段的 CRC 都和器件发来的完全一致：

```
[SHT] crc fail #1 raw=6B 04 0A 9D 1B 25
                    └─ 温度 ─┘  └─ 湿度 ─┘

crc8(6B, 04) = 0A  →  收到的第 3 字节就是 0A   ✓
crc8(9D, 1B) = 25  →  收到的第 6 字节就是 25   ✓
```

问题出在 `SHT30_CRC_BLOCK` 这个宏上。它原本定义成 **3**，注释还写着"2 字节数据 + 1 字节校验"，
把**校验值本身**也算进了被校验的区间。而 SHT30 的规矩是：器件对 2 个数据字节算 CRC、
把结果作为第 3 字节发出来，主机这边要做的只是「算前 2 字节，和第 3 字节比」。

```c
/* 改前：拿 3 个字节的 CRC 去和第 3 个字节比 —— 永远不相等 */
if (sht30_crc8(&ctx.raw[0], SHT30_CRC_BLOCK) != ctx.raw[2])   /* 那时 SHT30_CRC_BLOCK == 3 */

/* 改后 */
#define SHT30_CRC_BLOCK  2u
```

CRC-8 有个性质：若 `crc8(A,B) == C`，则把 C 再异或进去之后结果必然为 `0`，
也就是 `crc8(A,B,C)` 恒等于 `0x00`。拿这个 0 去和 `raw[2]`（真实校验值）比较，
除非校验值恰好是 `0x00`，否则**必然不相等** —— 所以这是"每次必失败"，而不是偶发的通信错误。

这个 bug 的表象极具误导性，看上去完全像硬件问题。当时依次排查了四个方向：
**器件供电、上拉电阻、时钟拉伸、总线锁竞争** —— 全都不是。最后能把它钉住，
靠的是把读到的原始字节直接打出来，而不是继续推理。

**教训：CRC 校验失败时，先怀疑校验区间，再怀疑信号质量。**

## 与 CubeMX 生成代码的边界

本工程基于 CubeMX 生成。有几处内容不在 CubeMX 的管理范围内，重新生成后需要确认。

### 历史：CMSIS-RTOS V2 的接入方式变过

工程最初用 CubeMX 6.15 + FW_F1 V1.8.4 生成，当时 CubeMX 不给 STM32F1 提供 CMSIS-RTOS V2 选项：
它的定义文件 `db/mcu/IP/FREERTOS-v8.0.0_Cube_Modes.xml` 里，`CMSIS_V2` 的白名单只有
F4/F7/G0/G4/H7/L1/L4/MP1/WB 这几个系列。那时的做法是让 CubeMX 按 V1 生成脚手架，
再手工把封装层换成 V2，一共做了 13 处手工改造。

CubeMX 6.18.1 起 ST 去掉了那条白名单，STM32F1 可以原生选择 V2。工程随后升级到
CubeMX 6.18.1 + FW_F1 V1.8.7 + FreeRTOS V10.3.1，并按 `.ioc` 里的 `CMSIS_V2` 重新生成。
上面 13 处里有 6 处不再需要（手工放置 `CMSIS_RTOS_V2` 目录、在 uvprojx 里换源文件、
把 IncludePath 指向 V2、`FreeRTOSConfig.h` 里那十几个 config 开关、删除 defaultTask、
手工补 `osKernelInitialize()`），现在由 CubeMX 自己生成。

### 重新生成后需要确认的内容

| 位置 | 内容 | 说明 |
|---|---|---|
| `.ioc` | FreeRTOS 接口选择 **CMSIS_V2** | 改回 V1 会与 `App/` 里的代码不兼容 |
| `.ioc` | IWDG 分频 `IWDG_PRESCALER_64`、Reload `1249` | 默认的 `_8` / `1250` 实际超时只有 250 ms，而喂狗周期是 500 ms，板子会不停复位 |
| `.ioc` | `NVIC.EXTI3_IRQn`、`NVIC.USART1_IRQn` 均使能，优先级 5 | 优先级数值必须不小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`，中断里要调 FreeRTOS 的 ISR 版 API |
| `MDK-ARM/*.uvprojx` | IncludePath 里的 `../App` | `Src/freertos.c` 要 `#include "app_tasks.h"` |
| `Src/freertos.c` | USER CODE 区调用 `app_init()` | 本项目代码的入口 |
| `App/` | 全部源码 | CubeMX 不管理这个目录 |

`App/` 目录和 USER CODE 区在重新生成时是安全的，前三项由 CubeMX 依据 `.ioc` 生成，
只有 uvprojx 里的 include 路径需要在重新生成后确认一次。

## 共享总线的并发验证（实测）

SHT30（`0x44`）与 SSD1306（`0x3C`）挂在同一路软件 I²C 上，靠 `i2c_transaction()`
里的互斥锁串行化。这把锁到底管不管用，用一次**单变量对照实验**验证过。

**方法**：摘掉 `i2c_transaction()` 里的 `osMutexAcquire` / `osMutexRelease`
（其余一行不改）→ 烧录观察 89 秒 → 恢复锁 → 重烧 → 再观察一遍作对照。

| 指标 | **摘锁（实验组）** | **恢复锁（对照组）** |
|---|---|---|
| `flush FAILED` | 49 → 136，**89 秒 +87 ≈ 0.98 次/秒** | **停止增长** |
| `nack` | 66 → 182，**+116 ≈ 1.3 次/秒** | **停止增长** |
| `crc` | 停在 1，**全程无变化** | 1 |
| **OLED 画面** | **局部区域不更新 / 跳字 / 整屏闪** | **正常** |
| `[ALM]` 报警位 | 在 `0x10`（正常）与 `0x50`（SHT30 读失败）之间反复跳 | 稳定 |

**三条结论**：

1. **两个错误速率与 TaskSensor 的 1 Hz 读取周期严格吻合**（0.98 / 1.3 次每秒，
   而传感器正是每秒读一次）—— **传感器每读一次，就破坏一次刷屏**。
2. **`crc` 全程未增长**：冲突的后果是"从机根本读不出一个合法帧"（表现为 NACK），
   而不是"读到了但字节错位"。两个计数器分工不同。
3. **三种可见现象各对应一种冲突落点**：局部不更新 = 某个 flush 分片（256 字节）
   被打坏、那两页保持旧内容；跳字 = 位时序在**字节内**被穿插，OLED 收到被污染的字节；
   整屏闪 = 冲突落在**分片边界**，整个刷新序列作废。

⚠️ 这是干净的单变量对照：同一块板、同一批线、同一工况，**唯一变量就是那把锁**。

> 顺带一个结论：`ssd1306_flush()` 的**单个分片（256 字节）实测耗时 > 100 ms**，
> 整屏 4 个分片约 **600 ms** —— 比早期估算的 150 ms **大一倍以上**，
> 而且**超过 TaskDisplay 自己 500 ms 的刷新周期**。见「设计取舍」一节的更正。

## 设计取舍

- **软件模拟 I²C 而不是硬件 I²C**。F103 的硬件 I²C 有出名的 BUSY 卡死勘误；
  本项目速率需求极低（1 s 读一次），软件模拟更可控，且总线事务是一个连续的临界区，
  互斥锁边界更清晰。代价是刷屏慢 —— ★ **实测整屏约 600 ms**（早期按 150 ms 估的，
  偏小一倍以上，见上一节），显示周期定在 500 ms，**总线基本一直被动用**。
- **SSD1306 刷新是全屏刷新，不是脏页刷新**。只刷新变化的页会更省总线时间，
  但实现复杂度上去了。★ **代价比当初估计的大得多**：整屏实测约 600 ms，而刷新周期是
  500 ms —— **总线占用率已经饱和**（早期按 150 ms 估出来的"约 30%"是错的）。
  这正是 SHT30 读取容易被"饿死"、`I2C_TIMEOUT_MS` 不得不放宽到 300 的根因。
- **滑动平均窗口取 8 点**。窗口越长读数越稳，但对光照变化的响应越慢，
  8 点在 50 ms 采样周期下约 400 ms 收敛。
- **上报数据用整数**。温度湿度按 ×100 传 int16，避免浮点传输和字节序争议。
- **报警阈值集中在 `app_config.h`**。温度湿度光照六条阈值都定义在一处，可按现场环境调整。
- **字库只覆盖可打印 ASCII**，不显示中文，需要的字符由 `Tools/gen_font.py` 生成。
